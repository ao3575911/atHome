# Research note: delegated authority for household agents

16 October 2026. This note states the question atHome is actually asking, what this repository has shown, and which questions are still open. It does not estimate a market size. No public source consulted for this note gives a defensible revenue figure for "agent identity" as a category, and inventing one would not help the decision.

## The question

A person wants software to act for them: read a profile, draft a message, and stop there. The receiver of that action needs to check three things without phoning a vendor on every call:

- which person the agent speaks for
- which action was granted
- whether that grant is still valid

That is capability security applied to an agent. The old version of the idea is a capability in the sense of Dennis and Van Horn: possession of an unforgeable token is the authority, and the token is specific. Later practical forms are Macaroons (attenuation and caveats), Biscuit and UCAN (signed, attenuable tokens), GNAP (grant negotiation instead of a shared API key), and SPIFFE (workload identity for services). W3C DIDs and Solid pods attack the same ownership problem from the document and storage side. None of those citations are an endorsement that atHome should become one of them. They are the prior art a reviewer will name.

atHome's specific bet is narrower than a global identity system. The root is a local name such as `krav@atHome`. Agents and services hang off that root. Tokens name an audience. Revocation and replay are checked before the action. The server is not supposed to be the only thing that can say no.

## What the code has established

The bet holds inside one process.

On 16 October 2026 the registry onboarded 1, 10, 100, and 1,000 persons. Each person had two services, one agent, one audience-scoped token, an allowed request, a replay, a denied vault delete, an audience mismatch, and a revocation. SQLite and JSON both scored 100 percent on those checks. At 1,000 people, SQLite took 24.8 seconds and 14.7 MB. Per-person latency stayed near 24–35 ms after startup. See `2026-10-16-scale-simulation.md`.

So the open research problem is not "can Ed25519 and a verifier express this policy." It can.

## What is still open

### Who holds the key

The literature assumes the holder of the capability is the subject. atHome's HTTP API mints the key and then refuses to export it. The development store writes an empty `privateKey` and cannot parse the record afterward. Production refuses to mint. The research gap is a custody ceremony that matches the verifier: client-generated Ed25519, passkey, or a KMS adapter whose signatures verify as Ed25519 over canonical JSON.

The passkey provider in the tree does not close that gap. It signs `JSON.stringify` output and returns a WebAuthn assertion. The verifier will not treat that as a manifest signature. The KMS type is a skeleton that calls functions the host must supply. Both are sketches of an answer, not an answer.

### What "still valid" means after a crash

Replay nonces and revocation records can sit in SQLite. Witness receipts are signed by a key created in memory when the witness service is constructed. A receipt is evidence only if a verifier knows that witness and the witness key is the same one next week. Durable witness identity is an open design choice: one published key, a threshold of witnesses, or no witness claim until then.

### How much authority a string should carry

`payment:send` and `vault:delete` verify as booleans. Safety research on agents keeps tripping on this. A token that means "may pay" without an amount or a payee is not a capability in the strict sense. It is a role bit. The interesting protocol extension is a caveat: maximum amount, destination, count, or a confirmation id the person signs separately. Macaroons and Biscuit exist because that caveat problem showed up in real systems.

### Who may take a name

Names are first-come strings. That is a fine local convention and a poor public namespace. The research choice is whether `name@atHome` is a petname only the owner's verifier cares about, or a global claim that needs dispute and recovery. The recovery routes in the API cannot be used by a client who never received a key. Recovery is unimplemented in practice until custody is fixed.

## Implication

Further papers, extra storage engines, and a larger web surface will not answer the open questions. The next informative experiment is one external verifier, in another process, checking a request from a key that was generated outside the server, after the server has been restarted. If that experiment works, the protocol has left the single-process result above. If it fails, the failure will be custody or canonicalization, and that is the research.
